# Requirements Document

## Introduction

This feature ports the Medicare design system from the legacy Vite + React app (`frontend-react/`) to the new Next.js App Router app (`frontend/`, TypeScript, Tailwind CSS v4, `src/` directory, `@/*` alias). It also adds a production-grade dark mode, a temporary `/design-check` verification route, and a new `frontend/DESIGN.md` that becomes the single source of truth for design.

The work is design-only. Pages, feature components, stores and business logic stay out of scope. Non-color light-theme values are copied exactly from the legacy code. Two owner-approved deviations apply: the base font changes from Satoshi to Montserrat Alternates (Requirement 2.8), and the color palette is replaced by the refined palette in `frontend/DESIGN.md` (Requirement 2.10). Satoshi is dropped. Where the root `DESIGN.md` disagrees with the legacy code, the code wins.

## Glossary

- **Legacy_App**: The Vite + React application in `/Users/karangupta/Project/Medicare/frontend-react/`, the source of all light-theme values.
- **Target_App**: The Next.js App Router application in `/Users/karangupta/Project/Medicare/frontend/`.
- **Design_System**: The set of tokens, utilities, keyframes, fonts, logo assets and theme infrastructure created in the Target_App by this feature.
- **Globals_Stylesheet**: The file `frontend/src/app/globals.css`.
- **Root_Layout**: The file `frontend/src/app/layout.tsx`.
- **Implementer**: The agent or developer who carries out this feature, creates commits and writes the final report.
- **Primitive_Token**: A CSS variable holding one raw color value with no usage meaning, for example a navy shade. The value is a hex or rgba literal or, for a color taken from a Palette_Utility, the Tailwind default palette value (an `oklch()` literal or a `var(--color-<name>-<shade>)` reference). Primitive_Tokens are the only place raw hex is allowed.
- **Semantic_Token**: A CSS variable named by purpose (for example `surface`, `text-muted`, `danger`) that references a Primitive_Token and has one value per theme.
- **Legacy_Token**: A token name that already exists in the Legacy_App `@theme`: `primary`, `secondary`, `accent`, `breakpoint-xs`, `font-montserrat`, `shadow-custom`. The names stay unchanged; `primary`, `secondary` and `accent` become theme-aware (Requirement 11.10).
- **Base_Font_Stack**: The font-family list used for `html`, `body` and `--font-sans`: the Montserrat Alternates next/font CSS variable first, then operating-system or generic fallback families, ending in `sans-serif`.
- **Palette_Utility**: A Tailwind utility named after a default palette color (for example `bg-white`, `text-black`, `text-gray-700`, `border-gray-100`, `hover:bg-gray-50`), including use through `@apply` inside a Legacy_App `@utility` class and use as a CSS variable such as `var(--color-gray-200)`.
- **Manual_Browser_Check**: A runtime check that needs a running server and a browser. The Implementer cannot run it under Requirements 8.1 and 15.4, so the project owner performs it from the step list in the Final_Report (Requirement 19.10).
- **Review_Stop**: The pause after each of the three commits in Requirement 18, during which the Implementer makes no file changes and no commits until the project owner replies "continue".
- **Theme_Mode**: One of the three user choices `light`, `dark` or `system`.
- **Resolved_Theme**: The theme actually applied (`light` or `dark`). When the Theme_Mode is `system`, the Resolved_Theme follows the operating system `prefers-color-scheme` setting.
- **Theme_Provider**: The client component in the Target_App that wraps `next-themes` and applies the `.dark` class to the `<html>` element.
- **Theme_Toggle**: The client component that lets the user choose a Theme_Mode.
- **FOUC**: Flash of unstyled or wrongly themed content; any rendered frame in which the page shows a theme different from the Resolved_Theme.
- **Hydration_Warning**: Any React or Next.js console message reporting a mismatch between server-rendered and client-rendered markup.
- **color-scheme**: The CSS property that tells the browser which theme native controls (scrollbars, form controls, date pickers) should use.
- **Contrast_Ratio**: The WCAG 2.x relative-luminance contrast ratio between two colors, ranging from 1:1 to 21:1.
- **Design_Check_Route**: The temporary page at `/design-check` in the Target_App used to review the Design_System visually.
- **Design_Doc**: The file `frontend/DESIGN.md`.
- **Root_Design_Doc**: The file `/Users/karangupta/Project/Medicare/DESIGN.md`, which documents the legacy design and loses to code when the two disagree.
- **Final_Report**: The Implementer's closing summary listing what was ported, what was added and what was skipped.
- **Allowed_Dependencies**: `next-themes`, `@tailwindcss/forms`, `@tailwindcss/typography` and `@tailwindcss/aspect-ratio`.

## Requirements

### Requirement 1: Scope boundary

**User Story:** As the project owner, I want this work limited to the design system, so that feature porting happens separately and stays reviewable.

#### Acceptance Criteria

1. THE Implementer SHALL limit the Target_App files created, modified, renamed or deleted by the feature commits (Requirement 18) to: the Globals_Stylesheet; the Root_Layout; the files that define the Theme_Provider; the files that define the Theme_Toggle; logo SVG files in `frontend/src/assets/logo/` (Requirement 7.1); favicon and app icon files in `frontend/src/app/` named per Next.js metadata file conventions (Requirement 7.4); files inside the Design_Check_Route folder (Requirement 14.1); the Design_Doc; `frontend/package.json`; `frontend/package-lock.json`; and files the project owner approved under criterion 7.
2. THE Implementer SHALL leave Legacy_App pages, feature components, stores, services and business logic unported, so that no Target_App file changed under criterion 1 contains markup, state management, data fetching or business logic copied from or reimplementing a Legacy_App page or feature component file, and so that the Design_Check_Route is the only route the feature adds.
3. THE Implementer SHALL leave every file under `frontend-react/` and the Root_Design_Doc unmodified, so that a diff between the commit before this feature and the last feature commit shows zero created, modified, renamed or deleted files under those two paths.
4. IF a design value occurs only in a Legacy_App page or feature component file and cannot be expressed as a token, utility class, keyframe or asset without copying that file's markup or logic into the Target_App, THEN THE Implementer SHALL leave the value unported and SHALL list it as skipped in the Final_Report with the value, the Legacy_App file path where it occurs and the reason.
5. WHEN writing Target_App code that uses a Next.js API (for example metadata, `next/font`, metadata icon file conventions or App Router layouts), THE Implementer SHALL use the API as documented in the Next.js 16.4.6 guides bundled in `frontend/node_modules/next/dist/docs/` and SHALL list the guide files consulted in the Final_Report.
6. THE Implementer SHALL use zero Next.js APIs in Target_App code that the bundled guides in `frontend/node_modules/next/dist/docs/` mark as deprecated.
7. IF a requirement in this document cannot be met without changing a Target_App file outside the list in criterion 1, THEN THE Implementer SHALL leave that file unchanged until the project owner approves the change, and SHALL list the file path and the requiring criterion in the Final_Report.
8. IF `frontend/node_modules/next/dist/docs/` is missing or has no guide for a Next.js API the Implementer needs, THEN THE Implementer SHALL ask the project owner before using that API and SHALL list the missing guide in the Final_Report.
9. THE Implementer SHALL leave `frontend/next.config.ts`, including its `reactCompiler: true` setting, unmodified, because this feature is design-only, and SHALL add one line to the Final_Report stating that `reactCompiler` is enabled and should be reviewed when feature porting starts (Requirement 19.11).

### Requirement 2: Light-theme value preservation (colors superseded by the palette refresh)

**User Story:** As a designer, I want the non-color light-theme values in the Target_App to be identical to the Legacy_App, and the colors to follow the refined palette, so that layout and behavior do not change and every color pair meets accessibility minimums.

> **Palette refresh (owner decision, supersedes the legacy color values in this document).** The refined palette in `frontend/DESIGN.md` sections 3.2 and 3.3 replaces the Legacy_App color values wherever this document requires a light-theme color to equal the Legacy_App. This covers Requirement 2 criteria 2, 3, 5 and 7 (color values only), Requirement 3 criterion 3 (the light values of `--color-secondary` and `--color-accent`), Requirement 4 (Primitive_Tokens), Requirement 11 criterion 10 and Requirement 12 criterion 3. Non-color values (breakpoint `xs`, `--shadow-custom` offsets and blur, class names, keyframes, layout and spacing utilities) still equal the Legacy_App. Every changed light value is an approved deviation listed under Requirement 2 criterion 10.

#### Acceptance Criteria

1. THE Design_System SHALL expose each Legacy_Token as a Tailwind theme variable with the same name used in the Legacy_App `@theme` block (`--color-primary`, `--color-secondary`, `--color-accent`, `--breakpoint-xs`, `--font-montserrat`, `--shadow-custom`), so that the Target_App build generates the same utility and variant names as the Legacy_App (for example `bg-primary`, `text-secondary`, `border-accent`, the `xs:` variant, `font-montserrat` and `shadow-custom`). The theme variable MAY hold a `var()` reference instead of a literal, as Requirement 11.10 requires for `primary`, `secondary` and `accent`.
2. WHILE the Resolved_Theme is light, THE Design_System SHALL give every Legacy_Token except `font-montserrat` a computed value equal to the computed value of the Legacy_App `@theme` value, compared as follows: for `--color-primary` (`#252a61`), `--color-secondary` (`#b8c5fd`) and `--color-accent` (`#e8c3d5`), the 8-bit sRGB red, green, blue and alpha channels of the color computed by `bg-primary`, `bg-secondary` and `bg-accent` are equal; `--breakpoint-xs` produces an `xs:` media query with a minimum width of `320px`; and `--shadow-custom` produces a computed `box-shadow` equal to that of `0px 10px 20px rgba(0, 0, 0, 0.2)`. The comparison uses computed values, not the declaration strings in the Globals_Stylesheet.
3. WHILE the Resolved_Theme is light, THE Design_System SHALL produce the same computed CSS property values as the Legacy_App for every `@utility` class and keyframe in the Legacy_App `src/index.css` listed in the Source findings. Values are compared with `getComputedStyle` on an element that carries the class, for every property the Legacy_App declares for that class, in the default, `:hover` and `:focus` states, at viewport widths of 320px, 640px, 768px, 1024px, 1280px and 1536px. For keyframes, the comparison covers every keyframe selector percentage and declared property. Color values count as equal when their 8-bit sRGB red, green, blue and alpha channels are equal. The only exceptions are the classes ported under Requirement 3.8 and the deviations listed under criteria 8 and 9. This criterion is verified by the project owner as a Manual_Browser_Check (Requirement 19.10).
4. IF the Legacy_App code and the Root_Design_Doc disagree on a value, THEN THE Implementer SHALL use the Legacy_App code value and SHALL list the disagreement in the Final_Report. Each entry SHALL give the item name, the Root_Design_Doc value, the Legacy_App value and the Legacy_App file paths where that value occurs (for example, hero gradient start `#1a1f4d` in the Root_Design_Doc versus `#1a1f4a` in code).
5. WHEN the Implementer replaces a hardcoded hex value with a Semantic_Token, THE Design_System SHALL give that Semantic_Token a light-theme computed color whose 8-bit sRGB red, green, blue and alpha channels equal those of the replaced hex value. Before comparison, 3-digit hex is expanded to 6 digits, and an 8-digit hex keeps its alpha channel.
6. THE Design_System SHALL keep the name `--font-montserrat` and SHALL set its value to a font-family list whose first entry is the Montserrat Alternates font loaded through `next/font/google` per Requirement 5.1 and whose last entry is the generic family `sans-serif`, matching the Legacy_App stack `'Montserrat Alternates', sans-serif` except that the first entry is the next/font CSS variable instead of the literal family name. This is the only Legacy_Token excluded from criterion 2.
7. IF a hardcoded hex value replaced by a Semantic_Token equals a Tailwind CSS v3 default palette hex under Requirement 4.7, THEN THE Implementer SHALL map the Semantic_Token to the Primitive_Token that holds the original hex value instead of to the Tailwind default palette variable, because Tailwind v4 defines its default palette in oklch and the palette variable can compute to 8-bit sRGB channel values that differ from the hex. THE Implementer SHALL also list the hex value, the palette variable name and both computed values in the Final_Report.
8. THE Implementer SHALL list the base-font change from Satoshi to Montserrat Alternates in the Final_Report as an intentional deviation from the Legacy_App light-theme values, with: CSS property `font-family` on `html` and `body`; Legacy_App value `'Satoshi', sans-serif`; Target_App value the Base_Font_Stack as written in the Globals_Stylesheet; and Requirement 5.4. THE Implementer SHALL list in the same way the `--font-sans` change from the Tailwind default to the Base_Font_Stack (Requirement 5.5).
9. IF another requirement in this document prevents a light-theme value from matching the Legacy_App, other than the deviations in criterion 8 (for example Montserrat Alternates now loading for `font-montserrat` under Requirement 5.1 when the Legacy_App never loaded it), THEN THE Implementer SHALL list each affected token or class in the Final_Report with the CSS property, the Legacy_App value, the Target_App value and the number of the requirement that caused the deviation.
10. THE refined palette in `frontend/DESIGN.md` sections 3.2 and 3.3 (51 Primitive_Tokens and 28 Semantic_Tokens, each declared in `:root` and `.dark`) SHALL replace the Legacy_App colors. Light and dark values SHALL equal the document, which `_checks/p06-light-values.check.mjs` verifies as 8-bit sRGB channels. THE Legacy_Tokens SHALL follow section 3.4: `--color-primary` is an alias of `brand` (light value unchanged), and `--color-secondary` and `--color-accent` take the `secondary` and `accent` values. Ported classes SHALL use Semantic_Token utilities only. THE legacy violet authentication color (`#4318ff`, `#3311db`), the role gradients, the `auth-primary`, `info`, `focus-ring`, chart, glass, skeleton, scrollbar and gradient Semantic_Tokens, and the `-fg` and `-text` status tokens are retired. THE Implementer SHALL list every changed light value (token, Legacy_App value, new value, reason) in the Final_Report as an approved deviation.

1. THE Theme_Toggle SHALL present exactly three options in the order Light, Dark, System, and each option SHALL have the accessible name "Light", "Dark" or "System" respectively, supplied by visible text or, for an icon-only option, by an `aria-label`.
2. THE Theme_Toggle SHALL expose its options either as an element with `role="radiogroup"` containing three `role="radio"` options that use `aria-checked`, or as an element with `role="group"` containing three buttons that use `aria-pressed`, and the group element SHALL have a non-empty accessible name that contains the word "Theme".
3. WHERE the Theme_Toggle uses `role="radiogroup"`, WHEN the Theme_Toggle has keyboard focus, THE Theme_Toggle SHALL follow the WAI-ARIA radio group pattern: Tab moves focus into the group onto the active option and the next Tab moves focus out of the group; Right Arrow and Down Arrow move focus to the next option and select it, wrapping from System to Light; Left Arrow and Up Arrow move focus to the previous option and select it, wrapping from Light to System; Space selects the focused option.
4. WHEN the user selects an option by mouse click, touch tap or keyboard, THE Theme_Toggle SHALL set the Theme_Mode to the matching value (`light`, `dark` or `system`) through the Theme_Provider within 100 ms of the selection and without a page reload, so that the choice persists per Requirement 9.5.
5. WHILE the Theme_Toggle has not mounted on the client, THE Theme_Toggle SHALL render a placeholder whose rendered width and height equal the mounted Theme_Toggle's width and height exactly (0px difference) and in which no option carries `aria-checked="true"` or `aria-pressed="true"`, so that the mount causes zero Hydration_Warnings and zero layout shift of surrounding content.
6. THE Theme_Toggle SHALL give each option a touch target with a rendered size of at least 44 by 44 CSS pixels at every viewport width from 320px upward, matching the 44px (`h-11` / `min-h-11`) touch targets used on Legacy_App mobile controls.
7. THE Theme_Toggle SHALL apply color only through Semantic_Token utilities and SHALL contain zero raw hex literals and zero Tailwind default palette color utilities (for example `text-white` or `bg-slate-100`).
8. WHERE the Theme_Toggle uses `role="group"` with `aria-pressed` buttons, WHEN the Theme_Toggle has keyboard focus, THE Theme_Toggle SHALL place all three buttons in the Tab sequence in the order Light, Dark, System and SHALL select the focused option when Enter or Space is pressed.
9. WHILE the Theme_Toggle is mounted, THE Theme_Toggle SHALL mark exactly one option as active (`aria-checked="true"` or `aria-pressed="true"`) and the other two options as `"false"`, with the active option matching the current Theme_Mode. System is the active option whenever the Theme_Mode is `system`, whatever the Resolved_Theme, including on first load with no saved Theme_Mode per Requirement 9.3.
10. THE Theme_Toggle SHALL show a visible focus indicator on the focused option with a Contrast_Ratio of at least 3:1 against the adjacent surface in both Resolved_Themes, and SHALL mark the active option with a cue other than color (an icon, a font-weight change or a border) in addition to any color change.

12. IF a token's value cannot be resolved in the current Resolved_Theme (the CSS variable is undefined or computes to an empty value), THEN THE Design_Check_Route SHALL still render the remaining swatches and samples, SHALL mark that swatch with a text label indicating the value is unresolved, and SHALL omit its Contrast_Ratio.

This covers every `@apply` of a default palette color utility with any variant prefix (for example `bg-white`, `text-black`, `text-gray-*`, `border-gray-*`, `bg-gray-*`, `hover:bg-gray-50`, `focus:ring-blue-100`, `focus:border-blue-300`, `bg-{green,yellow,red}-100`, `text-{green,yellow,red}-800`) and every `var(--color-<palette>-<shade>)` reference.
2. THE Design_System SHALL replace each Palette_Utility in criterion 1 with a Semantic_Token utility (or a `var()` reference to a Semantic_Token), keeping the same variant prefix and CSS property. While the Resolved_Theme is light, the token's computed color SHALL equal, in its 8-bit sRGB red, green, blue and alpha channels, the computed color the Legacy_App palette utility produced. Because the Legacy_App runs Tailwind `^4.1.8`, the reference is the Tailwind v4 default palette value; the Primitive_Token SHALL hold that palette value (the `oklch()` literal or a `var(--color-<name>-<shade>)` reference) instead of a converted hex, so that no rounding changes the light value.
3. THE Design_System SHALL give every Semantic_Token introduced under criterion 2 a dark value on `.dark`, and each dark value SHALL meet Requirements 11 and 12 for the pair the class uses (for example `card` background against the dark page surface, `form-label` text against the dark input surface, `status-badge-*` text against its badge background). Where one Semantic_Token already defined under Requirement 4 or 11 has the same light computed value and the same role, THE Design_System SHALL reuse that token instead of adding a new one.
4. THE Final_Report SHALL contain a table with one row per replaced Palette_Utility, with the columns: class (for example `card` or the border-color compatibility rule), legacy utility (with its variant prefix), Semantic_Token, light value (computed 8-bit sRGB and the source palette value), and dark value (hex). The table SHALL also appear in the Design_Doc section 3.
5. IF a Palette_Utility in a ported class has no role that maps to a single Semantic_Token, THEN THE Implementer SHALL still replace it with a dedicated Semantic_Token per criterion 2 and SHALL list it as ambiguous in the Final_Report under Requirement 17.3 with the class name.
6. THE Implementer SHALL leave Palette_Utilities used only in Legacy_App pages and feature components unported, per Requirement 1.4.

### Requirement 21: next-themes version and console warnings

**User Story:** As the project owner, I want the exact `next-themes` version recorded and any React 19 warning reported as it appears, so that I know whether the theme script is clean before shipping.

#### Acceptance Criteria

1. WHEN `next-themes` is installed, THE Implementer SHALL record in the Final_Report and the Design_Doc section 2 the version specifier in `frontend/package.json` and the exact version resolved in `frontend/package-lock.json`.
2. THE Implementer SHALL test Requirement 9.7 (zero Hydration_Warnings and zero other console warnings) against the recorded `next-themes` version, through the Manual_Browser_Check in Requirement 19.10 (b).
3. IF React 19.3.0 or Next.js 16.4.6 reports a console warning or error about the `next-themes` inline theme script (for example a warning about rendering a `<script>` tag inside a React component), THEN THE Implementer SHALL report the warning in the Final_Report with the exact message text, the `next-themes` version, the conditions that produce it and whether it affects the no-flash behavior of Requirement 9.6.
4. THE Implementer SHALL NOT suppress, filter or hide a warning under criterion 3, whether by patching `console`, adding `suppressHydrationWarning` to any element other than `<html>`, changing `next-themes` source, or changing the Next.js or React configuration. `suppressHydrationWarning` on `<html>` is allowed only for the `class` and `style` attributes that `next-themes` sets, as `next-themes` documents.
5. IF a warning under criterion 3 cannot be removed with the documented `next-themes` API, THEN THE Implementer SHALL list it under "Decisions needed" in the Final_Report with the available options, and SHALL leave Requirement 9.7 marked as failed for that warning until the project owner decides.
